## 1. 종합 판단

요구사항명세서는 기획서 v2.3의 핵심 방향을 충실히 반영한다. 핵심 기능 수준의 큰 누락이나 정면 충돌은 발견하지 못했다. 다만 **구현·검수 기준으로 확정하기 전에는 상태 전이와 예외 처리, 일부 AI 출력의 검증 기준을 보완해야 한다.** 개별 기능이 빠졌다기보다, 이미 정의된 규칙을 연결했을 때 처리 결과가 불명확한 상황들이 남아 있다.

기능 요구사항 **FR 70개**와 기능 확인 시나리오 **AC 27개**의 연결을 점검했다. AC에서 참조되지 않은 FR과 존재하지 않는 FR 참조는 모두 0개였다. 다만 식별자의 연결 여부와 실제 검증의 충분성은 별개다.

검토 당시 저장소에는 문서 3개만 있었으며 실행 코드·의존성 정의·테스트는 없었다. 따라서 이 검토는 문서상 설계와 검증 기준을 대상으로 하며, 실제 구현 결함이나 성능을 확인한 결과는 아니다. 기획서의 시장 통계·경쟁 서비스 현황에 대한 외부 사실 재검증은 포함하지 않는다.

### 1.1 우선순위 기준

| 우선순위 | 의미 |
| --- | --- |
| P1 | 핵심 흐름 설계 전에 우선 보완할 사항 |
| P2 | 해당 기능의 구현·검수 전에 확정할 사항 |
| 문서 정비 | 기능 정책과 별개로 문서의 사용성과 추적성을 개선할 사항 |

아래 지적은 현재 코드에서 문제가 발생한다는 뜻이 아니다. **명세의 문장만으로는 구현·검수 결과를 일관되게 결정하기 어려운 부분**을 설명한다. 원문 근거의 행 번호는 검토 시점 기준이며, 문서 수정 후에는 함께 표시한 절과 FR·AC 식별자를 기준으로 확인한다.

## 2. 우선 보완 사항

### 2.1 P1 상담 종료와 해당 상담의 견적 무효화 연결

**근거:** [명세서 §6.2 예약·견적 일관성 규칙][spec-consistency] 313행, [§6.3 정보 전달 단계][spec-disclosure] 328·339행, FR-QTE-05.

사용자가 기사를 선택 해제하면 상담이 종료되고, 재상담에는 새로운 선택이 필요하다. 그런데 견적 선택 불가 사유에는 만료·철회·제안 거절·다른 예약 확정은 있지만 **상담 종료·상담 상대 선택 해제**가 명시되어 있지 않다. 예약 확정 직전에 상담이 여전히 활성·수락 상태인지 검사한다는 규칙도 불분명하다.

사용자가 기사 A를 선택 해제한 뒤 이전에 열어둔 A의 미만료 견적 화면에서 예약을 확정하면, 새로운 상담 선택 절차를 우회하는 구현이 가능하다.

**수정 제안:** 상담 종료 시 해당 상담의 미확정 견적을 선택 불가로 전환하고, 예약 확정 시 상담 상태·사용자 선택·견적 유효성을 함께 재검사하도록 명시한다. 다른 기사로 예약을 확정했을 때의 기존 견적 무효화는 이미 규정되어 있으므로 유지한다.

**추가 검수:** 종료된 상담의 견적 선택, 상담 선택 해제와 예약 확정의 동시 요청.

### 2.2 P1 자가 해결 가이드 내용의 정확성 검수

**근거:** [명세서 §4.3 해결 경로 안내][spec-solutions] 132행의 FR-SOL-02, [§7 기능 확인 시나리오][spec-acceptance] 361행의 AC-02, [§8.2 평가 대상과 자료][spec-evaluation-data] 403~410행.

FR-SOL-02는 검증된 자료에 기반한 안내를 요구한다. 그러나 AC-02는 적용 조건·절차·주의사항·중단 기준 등의 표시 여부와 이후 경로 전환에 집중한다. 제8장의 평가표에도 **생성된 가이드가 원문의 조건과 절차를 정확히 반영했는지**를 확인하는 항목이 없다.

모든 구성요소가 있어도 적용 금지 조건을 반대로 설명하거나 중단 기준을 잘못 생성할 수 있다. 검증된 자료를 선정하는 것과 그 자료로 생성한 결과를 검증하는 것은 별개다. 제9장의 자료 선정·갱신 결정만으로 출력 내용의 검수를 대신할 수 없다.

**수정 제안:** 원문과 단계별 내용 일치, 적용 불가 사례에서 안내 차단, 중단 조건의 누락·반전 여부를 평가한다. 금지된 안내는 다른 항목의 평균 점수로 상쇄하지 않는 실패 조건으로 둔다.

**추가 검수:** 구성요소는 모두 있지만 내용이 원문과 충돌하는 가이드, 적용 불가 조건의 입력, 중단 조건이 누락되거나 반대로 생성된 결과.

### 2.3 P1 긴급 요청과 AI 처리 실패의 결합 상황

**근거:** [명세서 §4.14 공통 예외 처리][spec-errors] 263행의 FR-ERR-01, [§6.1 요청 처리 단계][spec-state] 293~294행, [§6.2 예약·견적 일관성 규칙][spec-consistency] 312행, AC-09·AC-17.

정상 흐름은 분석과 사용자 확인 후 해결 경로를 선택한다. AI 실패 시에는 재시도·보완을 제공하지만, 긴급 요청에서 분석이 계속 실패하거나 판단이 유보될 때 즉시 대응 안내로 진행하는 방법은 없다.

긴급 대응 우선 원칙 자체는 이미 잘 명시되어 있다. 남은 문제는 **AI 성공 여부에 의존하지 않고 그 원칙을 실행할 수 있는가**다.

**수정 제안:** 사용자 긴급 표시나 사전 정의된 긴급 입력이 있는 경우, AI 분석 완료를 기다리지 않고 검증된 대응 안내에 접근하는 경로를 정한다.

**추가 검수:** 긴급 요청과 AI 오류가 동시에 발생한 경우, 긴급 요청에 적합한 기사가 없는 경우. 정상 긴급 분기와 일반 AI 실패를 각각 통과한 것만으로 이 결합 상황을 검증했다고 보지 않는다.

### 2.4 P2 작업 내용 변경에 따른 견적 재확인

**근거:** [명세서 §4.2 AI 문제 파악 및 사용자 확인][spec-ai] 122행의 FR-AI-04, [§4.6 요청 검토 및 상담][spec-consultation] 170행의 FR-CON-03, [§6.2 예약·견적 일관성 규칙][spec-consistency] 314행.

지역·방문 가능 조건 변경 시에는 기존 견적을 재확인 상태로 전환하고 기사 재발행을 요구한다. 반면 추가 문답이나 사진으로 **수리 분야·작업 수량·작업 범위가 달라지는 경우**는 같은 수준으로 정의되어 있지 않다.

한 곳의 보수 견적을 받은 뒤 상담에서 두 곳의 보수가 필요하다고 확인되었을 때, 기존 금액·소요 시간으로 확정할 수 있는지 구현자마다 해석이 달라질 수 있다.

**수정 제안:** 견적의 전제가 되는 분야·범위·수량·예상 소요 시간을 정하고, 이 전제가 바뀌면 기사 재확인을 요구한다. 모든 사진 추가를 무효화 조건으로 삼을 필요는 없으며, 작업 조건에 영향을 주는 변경을 구분한다.

**추가 검수:** 지역·시간은 그대로인 상태에서 작업 수량이나 분야가 바뀐 경우, 작업 조건을 바꾸지 않는 참고 사진만 추가한 경우.

### 2.5 P2 작업 소요 시간과 사용자 가능 시간의 의미

**근거:** [명세서 §4.7 견적 및 방문 조건 제안][spec-quotes] 180행의 FR-QTE-02, [§6.4 동선 추천의 비교 기준][spec-route] 348~351행, [§9 세부 정책 결정 항목][spec-decisions] 473행.

작업·이동 시간을 포함한 충돌 검사는 이미 명시되어 있다. 제9장에도 모의 작업 시간과 출처를 결정하도록 되어 있다. 그러나 **추천용 예상 시간 → 기사 견적의 확인 시간 → 확정 예약의 점유 구간** 사이의 관계가 부족하다.

사용자 가능 시간이 14:00~15:00이고 제안 방문이 14:30, 예상 작업이 90분이면 허용되는 예약인지 판단할 수 있어야 한다. 현재 표현은 방문 시작만 시간대에 포함되면 되는지, 작업 전체가 포함되어야 하는지 불명확하다.

**수정 제안:** 사용자 시간대가 의미하는 범위를 확정하고, 견적에서 기사가 소요 시간을 확인하도록 연결한다. 추천 단계의 가정과 기사 확인 값을 구분하며, 소요 시간이 바뀌면 동선과 예약 가능 여부를 다시 검사한다.

**추가 검수:** 추천 때 30분으로 가정했지만 상담 후 90분으로 바뀐 경우, 방문 시작은 가능 시간에 포함되지만 작업 종료는 벗어나는 경우.

### 2.6 P2 기사 방문 불가와 작업 진행 중 취소

**근거:** [명세서 §4.9 예약 관리][spec-reservations] 206~207행, [§6.2 예약·견적 일관성 규칙][spec-consistency] 315~317행.

기사 일정이 충돌하면 기존 예약을 변경·취소하라고 안내하지만, 취소 권한은 사용자에게만 명시되어 있다. 기사가 실제로 방문할 수 없고 사용자가 변경을 거절하거나 응답하지 않으면 예약을 종결할 경로가 없다.

또한 현재는 **완료 처리 전까지 취소 가능**하므로 작업 중인 예약도 취소할 수 있다. 10:00~12:00 작업을 11:00에 취소하면 일정 점유가 해제되고, 취소된 예약에는 완료 처리를 할 수 없다. 이미 수행한 작업과 실제 점유 시간을 어떻게 남길지 빠져 있다.

**수정 제안:** 기사 방문 불가에 대한 취소 또는 대체 종결 절차를 정한다. 작업 중 취소는 방문 시작 전 취소로 범위를 제한하거나, 시작 후에는 작업 중단과 수행 내역을 남기는 방식으로 구분한다. 결제·환불·정산 기능까지 추가할 필요는 없다.

**추가 검수:** 기사 방문 불가 상태에서 사용자가 변경을 거절하거나 응답하지 않는 경우, 작업 시작 직전과 직후의 취소.

### 2.7 P2 방문 예정 시각이 지난 견적의 확정

**근거:** [명세서 §6.2 예약·견적 일관성 규칙][spec-consistency] 308·313행, FR-QTE-02·FR-RES-02.

현재 시각 검사는 견적 만료 여부에 적용된다. 방문 예정 시각 자체가 지났는지는 별도로 다루지 않는다.

방문 예정 10:00, 견적 만료 18:00인 제안을 11:00에 선택하면, 미만료이고 일정 충돌도 없다는 이유로 확정될 여지가 있다.

**수정 제안:** 확정·변경 시 방문 시각이 현재 시각을 기준으로 유효한지 검사하고, 견적 만료 시각과 방문 시작 시각의 관계를 정한다. 필요한 준비시간은 별도 정책으로 결정한다.

**추가 검수:** 방문 예정 시각 경과 후 확정, 확정 처리 도중 시간 경계를 통과한 경우, 지난 시각으로 예약 변경.

### 2.8 P2 제조사 AS 이후의 종료와 복귀

**근거:** [명세서 §6.1 요청 처리 단계][spec-state] 296~300행, FR-SOL-04.

제조사 AS는 외부 절차로 안내하고 플랫폼이 예약·완료를 자동 확정하지 않도록 되어 있다. 이 구분은 타당하지만, 외부 AS로 해결했거나 이용하지 못했을 때 사용자가 요청을 어떻게 정리하는지는 없다.

제조사가 해당 모델의 출장을 지원하지 않는 경우, 기존 사진·문답을 유지하면서 일반 기사 탐색으로 돌아갈 수 있어야 한다.

**수정 제안:** 사용자 확인으로 외부 해결 기록·종료, 미해결 시 해결 경로 재선택을 추가한다. 플랫폼의 외부 예약 자동 확인과는 구분한다.

**추가 검수:** 외부 AS로 해결한 경우, 외부 AS 이용이 불가능하여 같은 요청에서 기사 탐색으로 돌아가는 경우.

### 2.9 P2 상담 전달에 필요한 식별 정보 제거 정책의 결정 시점

**근거:** [명세서 §6.3 정보 전달 단계][spec-disclosure] 326행, [§9 세부 정책 결정 항목][spec-decisions] 477행.

상담 단계부터 사진·텍스트에 포함된 주소·연락처 등을 가리거나 제외하도록 요구한다. 그런데 제9장의 해당 방식 확정 시점은 “자료 공개·별도 활용 구현 전”으로 적혀 있어, 공개 포트폴리오 단계까지 미뤄도 되는 것으로 읽힐 수 있다.

**수정 제안:** 확정 시점을 “상담 등 최초 외부 전달 구현 전”으로 명확히 하고, 원본·가림 처리본의 구분과 처리 실패 시 전달 차단·보정 절차를 연결한다. 자동 탐지 구현을 필수로 정할 필요는 없으며, 프로토타입에서는 확인·수동 보정 방식도 선택할 수 있다.

**추가 검수:** 상담 사진에 식별 정보가 남은 경우, 가림 처리가 실패하거나 완료되지 않은 경우, 가림 처리본과 원본의 접근 권한이 다른 경우.

## 3. 기획서 v2.3과의 정합성

비교의 중심 근거는 [기획서 §7.1 구현 범위][plan-scope]와 [명세서 §1 적용 기준과 구현 범위][spec-scope]다.

| 비교 항목 | 판단 | 주요 근거 |
| --- | --- | --- |
| 사례 매칭·동선 할인 예약·경과 분석 및 인계 모두 구현 | 일치한다. 일부를 선택 기능으로 축소하지 않았다. | 기획서 §7.1, 명세서 §1.1~1.2 |
| 사진 변화 분석을 한 가지 문제 유형으로 제한 | 기획서부터 정한 제한이다. 명세서의 임의 축소가 아니다. | 기획서 §6.3·7.1, 명세서 §1.2·FR-HIS-04 |
| 사진 한 장으로 상담·예약·인계 진행 | 유지되어 있다. 경과 사진 수집 때문에 접수가 막히지 않는다. | 기획서 §4.1·6.3, 명세서 §3.1·FR-HIS-07 |
| 기사 자율 할인과 할인·최저가 미보장 | 일치한다. 시스템이 할인 금액을 임의 확정하지 않는다. | 기획서 §6.2, 명세서 FR-QTE-03·FR-FLX-04 |
| 실제·모의 사례 구분과 원본 근거 연결 | 일치하며 검수 기준도 구체화했다. | 기획서 §6.1·7.3, 명세서 FR-PRO-04·FR-MAT-03 |
| 단계별 정보 공개와 별도 활용 동의 | 기획 원칙을 상담·예약·종료 단계별로 상세화했다. | 기획서 §7.4, 명세서 §4.13·6.3 |
| 실결제·커머스·외부 연동 등 제외 | 기획서의 프로젝트 범위 구분과 일치한다. | 기획서 §7.1, 명세서 §1.3 |
| 모의평가와 실제 비용 절감·만족도 효과 구분 | 유지되어 있다. 평가 결과를 실제 사업 효과로 과장하지 않는다. | 기획서 §7.2, 명세서 §8.2 |

견적 버전, 복수 상담, 기사 참여 의사 단계, 종료 후 권한, 동선 정렬 공식은 **기획서보다 상세해진 정책 선택**이다. 명세서는 이를 `명세화`로 표시하므로 추가됐다는 이유만으로 기획 이탈이라고 판단할 수는 없다. 다만 이 정책들로 늘어난 상태·화면·검수 작업은 개발 범위에 반영해야 한다.

## 4. 검수와 AI 평가 체계

### 4.1 유지할 강점

다음 규칙은 이미 잘 마련되어 있다. 다시 누락으로 지적하기보다 구현·검수에서 실제 적용되는지 확인해야 한다.

- 사진 변화 유무, 영역·설명 정확성, 근거 연결을 따로 평가한다.
- 기준상 비교 가능한 사진을 모델이 비교 불가로 처리해도 평가 대상에서 임의 제외하지 않는다.
- 분모가 0인 결과, 평가 보류, 미정 목표값을 성공으로 처리하지 않는다.
- 접근 통제·동의·일정 충돌 위반을 AI 평균 점수로 상쇄하지 않는다.
- 견적 버전·만료·수정 전 제안 차단과 확정 당시 조건 보존을 명시한다.
- 동일 요청의 활성 예약 제한과 예약·일정 변경의 동시 처리 규칙을 명시한다.
- 상담별 자료 분리와 종료 후 원본 사진·다운로드 경로의 접근 통제를 명시한다.
- 인계서가 바뀌면 사용자가 다시 확인한 뒤 전달하도록 한다.

근거: [명세서 §6 상태와 처리 규칙][spec-state], [§8.4 지표 정의와 완료 판정][spec-metrics].

### 4.2 경계 사례와 관리 기능 검수 보강

[명세서 §7][spec-acceptance]은 모든 FR별 확인 기준을 함께 사용하도록 한다. 따라서 아래 지적은 FR 전체가 검수에서 빠졌다는 뜻이 아니라, **서술된 정책별 경계 사례와 검수 근거를 더 명확히 연결해야 한다는 뜻**이다.

| 보완할 검수 | 필요한 이유 | 관련 항목 |
| --- | --- | --- |
| 취소와 완료의 동시 요청 | 규칙은 있지만 일반 취소·재예약 시나리오만으로 검증되지 않는다. | §6.2 11번, AC-13·AC-14 |
| 변경안 수락 이후 조건 재수정 | 이전 버전의 수락이 새 조건에 재사용되지 않는지 확인해야 한다. | §6.2 12번, AC-13 |
| 공유 링크 철회 후 재열람 | 링크 방식을 채택하면 생성뿐 아니라 철회 결과도 확인해야 한다. | §6.3, AC-16 |
| 동선 동률·미산정·작업 시간 부족 | 정상적인 이동 시간 순위 비교 외의 분기도 검증해야 한다. | §6.4, AC-06 |
| 사례 등록→수정→검색 결과 반영 | 준비된 사례 검색만으로 실제 관리 기능을 검증할 수 없다. | FR-PRO-03, AC-04·AC-21 |

기존 AC에 하위 사례를 추가하여 입력·사전 상태·실행·기대 결과를 나누면 된다. 별도의 상용 기능을 추가하기보다 이미 정한 규칙을 재현 가능한 검수 항목으로 만드는 작업이다.

### 4.3 평가 실행 조건과 판정 신뢰성

[명세서 §8.1][spec-evaluation-process]은 데이터셋·정답·루브릭·목표값을 사전에 확정하고, 생성 에이전트와 평가 에이전트의 역할·대화 맥락을 분리한다. 이는 타당한 기본 구조다.

다만 평가 기록에는 다음 실행 조건도 연결하는 것이 좋다.

- 생성기와 평가기의 모델·프롬프트·설정.
- 검색 자료 버전과 평가 실행 식별자.
- 반복 실행의 횟수와 집계 방식.
- 평가자의 오판을 확인할 표본 검토 및 이견 처리 기준.

같은 데이터셋 버전으로 얻은 점수 차이가 기능 개선 때문인지 실행 조건 차이인지 구분하기 위해 필요하다. 역할·대화 맥락 분리가 이미 있으므로 이를 “독립 평가가 없다”는 문제로 볼 수는 없으며, 반드시 서로 다른 모델을 사용해야 한다는 뜻도 아니다.

## 5. 구현 가능성과 선행 결정

### 5.1 구현 범위의 타당성

제한된 프로토타입으로는 타당한 구성이다. 단일 문제 유형의 사진 분석, 고정된 모의 이동 시간표, 기준 사례·기사 데이터 사용은 구현 범위를 통제하는 적절한 선택이다.

다만 일정 내 완수 가능성을 판단할 근거는 부족하다. 기획서의 팀 구성만으로 과도한 범위라고 단정할 수는 없으며, 개발 일정·역량·자료 확보 상태를 함께 봐야 한다. 실제 부담이 큰 작업은 다음과 같다.

| 작업 | 주요 부담 |
| --- | --- |
| 사진 분석 평가 자료 | 비교 가능한 사진과 변화 영역·설명의 정답 자료 확보 |
| 정보 전달과 권한 | 원본, 상담 전달본, 인계본, 완료 후 열람본의 구분 |
| 견적과 예약 | 견적·변경 합의 버전, 예약·일정의 동시 처리 |
| 통합 검수 | 세 핵심 기능을 연결한 시나리오 실행과 평가 자료 작성 |

### 5.2 미정 사항과 누락의 구분

[명세서 제9장][spec-decisions]의 인증 방식, 지원 분야, 사진 제한, 평가 목표값 등은 이미 관리 중인 결정 과제다. 이를 단순 누락으로 세는 것은 부정확하다. 필요한 것은 실제 담당자·확정일·결정 결과를 연결하고 관련 구현 전에 기준을 확정하는 일이다.

| 선행 결정 | 영향을 받는 작업 |
| --- | --- |
| 초기 분야·서비스 지역·단일 사진 분석 유형 | 입력 화면, 분류 체계, 사진·사례 자료 확보와 정답 작성 |
| 업체 계정 구조와 기사별 일정 자원 | 접근 권한, 예약 점유, 동시 처리 |
| 사용자 가능 시간의 의미와 작업 소요 시간 | 견적, 동선 계산, 예약 충돌 검사 |
| 상담 전달본의 식별 정보 제거 방식 | 상담, 인계, 종료 후 조회 |
| 평가 자료·판정 기준·목표값 | 기능별 실험, 품질 판정, 최종 검수 |

성능·응답시간·재시도 한도 같은 비기능 기준은 이 파일이 기능 명세라는 점을 고려해 별도 검수 기준으로 관리하는 편이 좋다. 세 핵심 기능을 제외하기보다, 세 기능을 연결한 최소 시나리오를 먼저 구현하고 예외·동시성·권한 검수를 확장하는 순서가 기획과 부합한다.

## 7. 권장 수정 순서

1. **상담·견적·예약의 전이 규칙을 확정한다.** 상담 종료와 견적 무효화, 작업 내용 변경과 견적 재확인, 기사 방문 불가의 종결 절차를 연결한다.
2. **시간 모델과 취소 경계를 결정한다.** 사용자 가능 시간의 의미, 작업 소요 시간의 확인 주체, 지난 방문 시각의 확정 차단, 작업 시작 전후 취소를 정한다.
3. **긴급·실패 경로와 전달본 처리를 연결한다.** AI 실패 시 긴급 안내와 상담 단계의 식별 정보 제거 정책을 먼저 확정한다.
4. **검수 기준을 보강한다.** 자가 해결 가이드의 내용 정확성, 정책별 경계 사례, 평가 실행 조건을 기록한다.
5. **요구사항·시나리오·결정 기록을 함께 갱신한다.** 변경된 정책의 담당자·확정일·버전을 남기고 영향을 받는 검수 항목을 다시 확인한다.

이 검토서는 수정 제안과 판단 근거를 기록한 문서다. 요구사항명세서, 기획서, 기존 추가사항 분석 문서의 내용은 이 검토서 작성으로 변경하지 않았다.
